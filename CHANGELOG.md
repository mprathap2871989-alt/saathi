# Changelog

All notable changes to Saathi are documented here. Format loosely follows
[Keep a Changelog](https://keepachangelog.com/). Newest entries at the top.

## [Unreleased]

### Added
- **Admins now get an email when a new report is submitted.** New `src/lib/email.ts` — a minimal Resend wrapper with one function so far, `notifyAdminOfNewReport()`. Wired into `reportPost`/`reportComment` immediately after `prisma.report.create()` succeeds, so no email fires on the unauthenticated, duplicate-report (silent dedupe), or rate-limited paths. Email is intentionally minimal: report type, content ID, reason, timestamp, and a link to `/admin` — no reporter identity, no full post/comment content. Awaited (not fire-and-forget) so a serverless runtime can't terminate the function before the send completes, but `notifyAdminOfNewReport()` internally catches every failure (missing config, network error, Resend API error) and only logs — it never throws, so a broken/unconfigured mailer can never block or roll back a report. Added `EMAIL_FROM` to `.env.example`, defaulting to Resend's built-in `onboarding@resend.dev` test sender if unset, which works with zero domain setup but only delivers to the Resend account's own address until a real domain is verified.

### Changed
- **Category data now has exactly one source of truth.** `prisma/seed.ts` previously hand-typed a second, independent copy of all 13 categories' id/label/emoji/description/order — identical in content to `src/lib/categories.ts`'s `CATEGORIES` array but requiring every future category change to be made correctly in two places. `SETUP.md`'s production setup guide had a *third* hand-typed copy, as a raw SQL `INSERT` block. `prisma/seed.ts` now derives its category rows directly from `CATEGORIES` (`color` intentionally dropped — it's a UI-only concern with no DB column); `SETUP.md` now points to a new `npm run db:seed:categories` script (added `--categories-only` flag support to `prisma/seed.ts`, reusing the same seeding code path rather than the demo-data-inducing full `db:seed`) instead of a hand-maintained SQL block. Verified the derived output is byte-for-byte identical to the old hardcoded array — same 13 rows, same order, same content. No schema change, no data migration, no behavior change: `Category` table, `Post.categoryId` FK, and every UI consumer of `CATEGORIES` (already the single source for the running app — `prisma.category` is never queried as a list anywhere at runtime) are unaffected.

### Security
- **CRITICAL: Upgraded `next` from `15.1.0` to `15.2.9`, closing the remaining Phase 1 release blocker (C2).** The task's named target (`15.2.3`, the version that fixes CVE-2025-29927, the middleware-authorization-bypass CVE that motivated this upgrade) turned out to itself be vulnerable to a second, more severe issue discovered since: **CVE-2025-66478**, a CVSS 10.0 remote-code-execution vulnerability in the React Server Components protocol affecting Next.js 15.x/16.x App Router applications — which Saathi is. Checking further, even the first patch for *that* (`15.2.6`) had its own follow-up advisory from Next.js's December 11, 2025 security update (CVE-2025-55183/55184, later found incomplete and re-patched as CVE-2025-67779). The actual current, non-deprecated patch for the 15.2.x line is `15.2.9`, published the same day as this fix — confirmed via `npm install` producing zero deprecation warnings (npm's registry flags known-vulnerable exact versions directly at install time; both `15.2.3` and `15.2.6` triggered this warning explicitly, `15.2.9` did not). Deliberately stayed within the 15.2.x line rather than jumping to `15.5.x` (Next.js's newer officially-designated Maintenance LTS branch, per the `backport` dist-tag) or Next.js 16 — logged as follow-up tech debt below, not pulled into this task's scope.
- As a side effect, this upgrade also resolves a pre-existing peer-dependency conflict: `@clerk/nextjs@6.39.6` peer-requires `next: "^15.2.3"` (among other ranges), unmet by the previous `15.1.0` pin since Task 1, worked around each time with `--legacy-peer-deps`. `npm install` now succeeds cleanly with no peer conflict and no flag needed.

### Fixed
- **CRITICAL: `/create`, `/profile`, and `/admin` no longer crash on every request.** `src/middleware.ts` called `auth().protect()`, but in the installed `@clerk/nextjs@6.39.6`, the middleware's `auth` callback parameter is `async` — calling it returns a `Promise`, which has no `.protect` method, throwing `TypeError: auth(...).protect is not a function` on every request to a protected route. Identified in the Phase 1 Release Readiness Audit, confirmed via a live dev-server reproduction with an exact stack trace before any fix was attempted.

  Fixed in two steps, the first of which I caught and corrected myself during verification rather than shipping incomplete: an initial `auth().protect()` → `auth.protect()` change removed the crash, but left the callback non-`async` and the call un-awaited — verifying against a live server showed this silently let unauthenticated requests through with the raw page content (200, full form HTML) instead of blocking them, because Clerk's internal redirect signal from `protect()` never got awaited long enough for Clerk's own middleware wrapper to catch and convert it into a real HTTP response. Corrected to `clerkMiddleware(async (auth, req) => { if (isProtectedRoute(req)) await auth.protect(); })`, matching Clerk's documented v6 API exactly.

  Re-verified live post-fix: zero `TypeError`s and zero unhandled promise rejections anywhere in the log (both previously present, now absent). Unauthenticated requests to all three protected routes now correctly receive `404` (Clerk's documented fallback when it can't resolve a real sign-in redirect target from placeholder credentials — explicitly acceptable per this task's own verification criteria) instead of either a 500 crash or a leaked 200 with real page content. Public routes (`/`, `/community`) were unaffected throughout — their residual 500s in this sandbox are a confirmed, wholly unrelated cause (`@prisma/client did not initialize yet` — no generated Prisma client available in this environment), the same cause already present before this fix.
- **Comment "helpful" votes now persist across page reloads.** `getPost()` previously fetched the current user's vote state for the *post* but never for its comments, so `CommentItem` always mounted with `voted=false` regardless of the real DB state — clicking an already-voted comment would silently remove the vote instead of adding one. `getPost()` now batch-fetches the user's comment votes in one additional query (not N+1) and returns a `userHelpful` flag per comment; `CommentItem` takes a new `initialUserHelpful` prop and initializes from it. Also fixed: on a successful toggle, `CommentItem` now syncs `count`/`voted` to the server's authoritative response (matching `HelpfulButton`'s existing correct pattern) instead of only reverting on error and otherwise trusting the optimistic guess.
- **Concurrent helpful-vote toggles (double-click, two tabs) no longer throw uncaught exceptions.** The `findUnique` → `create`/`delete` sequence in `togglePostHelpful`/`toggleCommentHelpful` wasn't atomic — two near-simultaneous toggles could both read "no existing vote" and both attempt `create()`. The DB's unique constraint already prevented the count from ever inflating, but the losing request's `create()` threw an uncaught exception that neither `HelpfulButton` nor `CommentItem` caught, leaving that client's optimistic UI stuck in a state the server had actually rejected. Both toggle functions now catch the two expected race outcomes (unique-constraint on create, not-found on delete) and resolve to the correct end state instead of throwing; any other, unexpected error still propagates normally.
- **Report submission now rate-limited (10/day per user).** `reportPost`/`reportComment` previously had no cap on distinct reports across different posts/comments — a bad actor could flood the moderation queue. Added a shared `hasReachedDailyReportLimit()` helper (scoped to `reports.ts`, used by both functions) mirroring the exact daily-count pattern already used in `createPost` (3/day) and `createComment` (10/day): count today's reports for the user, block at the limit, same `>=` boundary semantics. Limit chosen to match the existing comment limit as a reasoned anchor rather than a new guess, extracted into a single `DAILY_REPORT_LIMIT` constant. `ReportButton.tsx` needed no changes — it already correctly displays `{ error }` responses. Purely additive to `reports.ts` (25 insertions, 0 deletions) — `resolveReport`/`getPendingReports` untouched.
- **Admins can no longer suspend their own account.** `suspendUser()` had no guard against an admin targeting themselves, with no un-suspend UI anywhere in the codebase to recover from it. Added a check comparing the acting admin's own DB id against the target id, returning `{ error: "You cannot suspend your own account." }` instead of performing the update. Also fixed `AdminTabs.tsx`'s `handleSuspend`, which previously ignored `suspendUser`'s return value entirely and would show a false "User suspended." success toast even when the server rejected the request — it now checks the result and shows a distinct error-styled toast (extending the existing toast component with a `type` field, defaulting to `"success"` for the three other unmodified call sites).
- **`/create` now pre-selects a category from the URL.** `category/[slug]/page.tsx`'s "Share your story" link has always pointed to `/create?category=<id>`, but the create page never read that param — users arriving from a category page landed on a blank category picker. `useSearchParams()` now initializes the selected category, validated against the real `CATEGORIES` list so an unknown or hand-typed value safely falls back to no selection instead of a broken state. Required wrapping the form in a `<Suspense>` boundary per the App Router's requirement for `useSearchParams()` — the default-exported `CreatePage` component is now a thin Suspense wrapper around the unchanged form logic (moved into `CreatePageForm`), with no visual or behavioral change to the form itself.
- **Content blocklist now actually filters content.** `containsBlockedContent()` previously checked against a two-word placeholder array (`["slur1", "slur2"]`) and blocked nothing in production. It now uses `obscenity`, a maintained profanity/slur-detection library with word-boundary matching and evasion handling (leetspeak, character repetition), wired in via a new `src/lib/blocklist.ts` module. `posts.ts` and `comments.ts` required no changes — the exported function signature from `src/lib/utils.ts` is unchanged.
