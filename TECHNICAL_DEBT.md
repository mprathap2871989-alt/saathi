| `handleRemovePost`/`handleRemoveComment`/`handleDismiss` don't check server action results | Same pattern `handleSuspend` had before this task's fix — these three call `await removePost(...)`/`removeComment(...)`/`resolveReport(...)` and unconditionally update local state + show a success toast, regardless of whether the action actually returned `{ error }`. Currently low-impact since those three actions rarely fail for a legitimate admin, but it's the same silent-failure shape that was worth fixing for `suspendUser`. Not fixed here — touches handlers unrelated to today's self-suspend-guard task. | Low-Medium | Phase 1, small follow-up (reuses the `toast.type` infrastructure already added this task) |
| Rate-limit logic duplicated three times (`createPost`, `createComment`, `reportPost`/`reportComment`) | Each of `posts.ts`, `comments.ts`, and now `reports.ts` has its own inline (or, for reports, locally-scoped) daily-count-and-compare implementation, rather than one shared helper used everywhere. `reports.ts`'s new `hasReachedDailyReportLimit()` was deliberately scoped to that file only, to avoid retrofitting the already-working `createPost`/`createComment` implementations as an unrelated refactor inside a single-purpose task. | `email.ts` has no delivery confirmation / retry | `notifyAdminOfNewReport()` attempts exactly once and logs-and-swallows on any failure, by design (reporting must never be blocked by email). This means a transient Resend outage silently drops that one alert with no retry and no record beyond a server log line. Acceptable today since reports still land in `/admin` regardless of whether the email sends — the email is a convenience nudge, not the source of truth. Worth revisiting only if real usage shows admins missing reports because of dropped alerts specifically (as opposed to just not checking `/admin` often enough, which an email retry wouldn't fix anyway). | Low | Not scheduled — revisit only if evidenced by real moderation gaps |
| `sender uses onboarding@resend.dev by default` | Functional but restricted — only delivers to the email address tied to the Resend account itself until a custom domain is verified in the Resend dashboard and `EMAIL_FROM` is set accordingly. Fine for a single-admin early-stage deployment where `ADMIN_EMAIL` likely *is* that account's address; will silently stop delivering the moment `ADMIN_EMAIL` is changed to a different address without also verifying a domain. | Low-Medium | Whoever configures production `ADMIN_EMAIL` should verify a domain in Resend at the same time — noted here so it isn't discovered as "why did my alert email never arrive" |
| No shared Prisma race-condition helper | `isUniqueConstraintError()`/`isRecordNotFoundError()` were added directly in `votes.ts`, scoped to that file's two toggle functions. Not extracted preemptively — no second consumer exists yet. | Low | Revisit only when a second real consumer appears |
